# EA9 Windows Updater

Requirements and design: **[spec.md](spec.md)**. Read it before changing anything here.

A single-file Windows GUI (`Community EA9 Firmware Updater v<ver>.exe`, .NET Framework 4.8) that writes the EA9 firmware over USB HID. The release image, its patch table and `changelog.txt` are embedded in the exe. Before writing, the exe patches the user's focal length and lens name into the image.

## Prerequisites (Linux)

- ARM toolchain and ASF4 for the firmware build: see the repo README, section 4. The defaults are `~/opt/arm-gcc` and `~/opt/asf4/samd21`.
- .NET SDK 8.x. It is installed in `~/.dotnet`. Set `DOTNET=/path/to/dotnet` to use another one.
- python3.

## Build

```sh
tools/win_updater/build.sh
```

Output: `tools/win_updater/out/Community EA9 Firmware Updater v<ver>.exe`. Ship that one file.

What it does:
1. `locate.py -o firmware/patchmap.json --bin firmware/ea9.bin`
   - runs `make release`
   - builds two scratch variants with other focal/name values
   - finds the patch fields and verifies them byte for byte
2. `dotnet build EA9Updater.csproj -c Release -o out`, embedding `firmware/*` and `changelog.txt`.

If `locate.py` fails, the source changed in a way that moved or folded the focal length or name fields. Its message says where. See spec.md 5.1–5.2.

## Common tasks

| Task | Where |
|---|---|
| Edit release notes | `changelog.txt`, then rebuild |
| Bump firmware version | 0x07 template byte in `src/emount_packets.c` (BCD) **and** `Firmware.DeclaredVersion` in `src/Firmware.cs` |
| Change focal range or name rules | `Firmware.cs` (`FocalMinMm`/`FocalMaxMm`, `CheckName`); keep `spec.md` 5.4 in step |
| Change the UI | `src/MainForm.cs`. The layout is written in code; there is no designer |
| Check a patch table by hand | `python3 -I tools/win_updater/locate.py -o /tmp/p.json` prints the fields |

## Files

| File | Content |
|---|---|
| `spec.md` | requirements, patch-table contract |
| `locate.py` | release step: builds A/B/C, writes `patchmap.json` and the image |
| `build.sh` | locate + dotnet build |
| `EA9Updater.csproj`, `app.manifest` | net48 WinExe, no `.exe.config` |

| `src/Flasher.cs` | bootloader protocol; mirrors `tools/ea9flash.py` |

| `src/MainForm.cs`, `src/Program.cs` | UI |
| `firmware/` | generated by `build.sh`, git-ignored |
| `out/`, `bin/`, `obj/` | build output, git-ignored |

## Testing

There is no Windows in the build environment. Logic that does not touch Windows APIs (`Flasher.cs`, `Firmware.cs`) can be tested on Linux. Compile those files into a .NET 8 console project, together with `Hid.cs` for the `IReportChannel` interface. Drive `Flasher` with a fake `IReportChannel` that plays the bootloader. Compare `Firmware.Patch()` output against `locate.apply_patch()`.

### UI under Wine (layout smoke test)

Wine runs the exe on Linux using wine-mono in place of .NET Framework. Use it to check that the window opens and the resources load. A broken image or patch table makes the status line say "This updater is damaged". Fonts, button styles and the progress bar look different from Windows, so judge the final look on Windows.

One-time setup (Ubuntu). A separate prefix keeps `~/.wine` untouched:

```sh
sudo apt install wine winetricks
export WINEPREFIX=~/.wine-ea9
WINEDLLOVERRIDES="mscoree,mshtml=" wineboot -i     # create the prefix, skip the mono prompt
curl -LO https://dl.winehq.org/wine/wine-mono/9.4.0/wine-mono-9.4.0-x86.msi
wine msiexec /i wine-mono-9.4.0-x86.msi /qn        # 9.4.0 is the version Wine 10.0 expects
```

Run:

```sh
WINEPREFIX=~/.wine-ea9 wine "tools/win_updater/out/Community EA9 Firmware Updater v2.0.0.exe"
```

Screenshot without a desktop (e.g. for an agent): start a virtual display, run the exe there, and grab it:

```sh
sudo apt install xvfb
Xvfb :99 -screen 0 1280x900x24 &
DISPLAY=:99 WINEPREFIX=~/.wine-ea9 wine "tools/win_updater/out/Community EA9 Firmware Updater v2.0.0.exe" &
python3 -c "from PIL import ImageGrab; im=ImageGrab.grab(xdisplay=':99'); im.crop(im.getbbox()).save('ui.png')"
```

Under XWayland, `ImageGrab` on the real display fails (`X get_image failed`), so use Xvfb.

Wine has not been used to test the HID path. Its USB HID passthrough depends on the Wine version and configuration. Do not flash a real adapter through Wine: a transfer cut halfway bricks the adapter until it is recovered over SWD.

### Real hardware

The HID layer can only be trusted on Windows, with the adapter on USB (not on a camera).
